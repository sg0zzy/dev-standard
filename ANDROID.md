# Android package and update contract

Applies only to declared Android targets. Build matrix selection is owned by [BUILD.md](BUILD.md); external Play delivery by [DISTRIBUTION.md](DISTRIBUTION.md).

## Package types and signing

| Target | Required treatment |
| --- | --- |
| Local/ordinary CI debug APK | Clearly test-only; debug signing MAY be generated by the toolchain. No promise of production updates. A distinct application ID SHOULD avoid conflicts. |
| Beta APK | Release packaging and declared production-compatible signer for promised update paths; verify final signature. |
| Stable APK | Declared release signer; verify certificate and installability. |
| Google Play AAB | Upload-signed with the configured credential; Play delivers APKs under its app-signing arrangement. AAB is not a directly installable APK. |

Projects MUST declare application IDs, allowed signer certificate fingerprints/lineage, supported OS versions and promised update edges (beta→beta, beta→stable, stable→beta, stable→stable, and cross-destination where relevant). Do not promise every edge automatically. Each promised update MUST have a compatible application ID, signing identity/validated rotation lineage, versionCode order and compatible application/data behavior. Projects SHOULD test data preservation across supported edges.

Never assume that an APK signed by a Play **upload key** can update an APK signed by a different **app signing key**. Cross-GitHub/Play updates require validating the actual certificates on installed APKs and supported devices. If compatibility is unavailable, projects MUST document separate IDs/channels or explicitly unsupported transitions. Key rotation requires an explicit plan and device/OS verification; do not assume matching a new certificate alone covers older devices. See [Android app signing](https://developer.android.com/studio/publish/app-signing).

Production keys MUST NOT be generated, rotated or replaced automatically. Credentials MUST be excluded from repositories, packages, logs and ordinary artifacts; use GitHub Actions Secrets or protected environments as appropriate. Release APKs MUST pass signature verification against the declared identity before being called installable release packages. Unsigned or wrong-signer APKs MUST block their mandatory release target. Debug signing MUST NOT serve as a production fallback.

## Monotonic versionCode

Projects MUST document a versionCode allocator covering all promised updates and existing codes, including store submissions not yet published. The recommended strategy is a durable monotonic integer sequence per application/update-compatibility domain, **independent of SemVer arithmetic**. One coordinated domain SHOULD cover GitHub APKs and Play AABs if cross-destination updates are promised. Distinct IDs MAY have separate domains.

Under this strategy:

1. Before official packaging, reserve a code strictly greater than every previous allocated, submitted or distributed code in the domain. Seed from an inventory of existing Play and GitHub packages; use zero only when none exist.
2. Serialize reservations atomically, persist the release-to-code mapping durably, and never reuse abandoned codes. Timestamps and workflow run numbers alone are insufficient without domain-wide ordering and collision checks.
3. Map each official release to its reserved code in metadata. APK/AAB variants for the same release MAY share a code only when the platform accepts that arrangement; document split/multi-APK requirements and reserve a greater code/range when necessary.
4. Before delivery, validate every supported upgrade edge. A stable following a beta MUST have a greater code for beta→stable updates. VersionCode order does not follow from versionName/SemVer order.
5. Treat retries of the same unpublished release as the same reservation. For an already submitted/distributed package, retry its exact bytes or promote the existing store artifact; a new binary needing a new code MUST be a new release identity under this policy.
6. Reject nonintegers, zero, negative values and values above **2,100,000,000** for Play-bound packages. This profile SHOULD use the same bound for all Android official packages to preserve future Play compatibility. At exhaustion MUST stop and plan migration; MUST NOT wrap or reset.

Android exposes versionName to users and uses versionCode for update ordering; Google Play imposes an upper bound and does not permit reusing an uploaded code for a new upload. See [Android versioning](https://developer.android.com/studio/publish/versioning). A globally monotonic sequence is this standard's conservative policy, not a claim that every Play track has identical promotion semantics.

Local/debug code allocation MUST NOT consume production reservations. A separate app ID SHOULD be used. If local testing uses a production ID, projects MUST document that arbitrary high local codes or different keys may block subsequent official updates and provide a safe test-device procedure. Uninstalling with potential data loss is not evidence of a successful promised upgrade.

Future major/minor increments and skipped development cores simply consume the next sequence value; no digit-width allocation is required. Existing encoded schemes MAY be retained if they prove all promised ordering edges, limits, concurrency, exhaustion and migration behavior. A migration MUST choose codes above all historical/submitted codes and test its boundaries. See [worked examples](examples/android-versioning.md) and Android cases in [COMPLIANCE.md](COMPLIANCE.md).
